# Contributing

Thank you for taking the time to improve this project. It is a small static HTML and Bootstrap exercise, so contributions should keep the examples easy to open, understand, and run without a build system.

## Before you start

- Read the README and the relevant page in Assignment_14_Bootstrap.
- Check existing issues and pull requests for duplicate work.
- For a substantial change to the purpose or structure, open an issue first to discuss the approach.
- Do not commit credentials, private data, generated caches, or unrelated IDE files.

## Making a change

1. Fork the repository and create a focused branch from main.
2. Keep each change scoped and use descriptive commit messages.
3. Preserve the relative media paths, Bootstrap 5.3.2 CDN links, integrity attributes, and responsive viewport tags unless the change intentionally updates them.
4. Use semantic HTML, descriptive accessible names, meaningful image alt text, and labels associated with form controls.
5. Do not present the sample modal as real authentication or wire it to a real credential collection service without an explicit security design.
6. Verify that the affected page opens in a browser and that local images, responsive layout, dropdowns, carousel controls, and modal behavior still work.
7. Update the documentation when page behavior, setup, licensing, or project scope changes.

## Images and third-party resources

Only contribute assets that you created or are permitted to redistribute. Record the source and license for new third-party media. A source-code MIT license does not automatically cover the existing or newly added images. Avoid embedding secrets or tracking identifiers in assets or markup.

## Submitting a pull request

Describe the user-visible change, list the files or pages affected, and state how you checked it. Include before/after screenshots for visual changes when practical. Keep the pull request focused and respond to review feedback with follow-up commits. Do not claim that the sample has a backend, working enrollment, or real authentication unless those capabilities have actually been implemented and documented.

## Review

Changes are reviewed for correctness, clarity, accessibility, appropriate asset rights, and consistency with the repository's static educational scope. There is no automated test suite or guaranteed review timeline at present.
